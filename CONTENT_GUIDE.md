# Как наполнить приложение контентом

Весь контент делается так: вы кладёте **скриншоты** и **текстовый файл** в папку своей карты `content/<карта>/` (например `content/cache/`), запускаете **один скрипт**, он режет кадры, рисует прицел и сам создаёт код для приложения. Руками в коде ничего писать не нужно.

```
content/
└── cache/                               <- одна папка на карту (имя: строчные латинские буквы и цифры)
    ├── lineups.txt                      <- описание лайнапов (координаты, названия, тип броска)
    └── screens/
        ├── cache_smoke_a_site_from_garage.png
        ├── cache_smoke_heaven_from_garage.jpg
        └── ...                          <- по одному скриншоту на лайнап

Карт может быть несколько (`content/cache/`, `content/mirage/`...). Id лайнапов в `lineups.txt` должны быть уникальными **только в пределах карты**: в приложении скрипт сам превращает `smoke_a` в `<карта>_smoke_a` (например `cache_smoke_a`), поэтому на разных картах id могут совпадать, а скриншот называется по короткому id (`smoke_a.png`).
```

---

## 1. Один раз: подготовка

1. Установите библиотеку для работы с картинками (один раз):

   ```bash
   pip install pillow
   ```
2. Радар Cache уже лежит в `app/src/main/res/drawable-nodpi/cache_radar.png` и подключён.

## 2. Как делать скриншот лайнапа

Скриншот должен быть сделан так, чтобы **прицел был наведён строго в нужную точку**. Эта точка окажется в центре кадра.

1. Встаньте на позицию броска.
2. Наведите прицел в нужный ориентир (угол окна, антенна, текстура на стене) максимально точно.
3. **Уберите из кадра всё лишнее**, иначе оно попадёт в тренировку: свой прицел и интерфейс. В консоли (нужен `sv_cheats 1`):
   - `cl_drawhud 0` — скрывает интерфейс и прицел;
   - `r_drawviewmodel 0` — скрывает гранату в руке.

   (Эти команды я не проверял на текущей версии CS2. Если какая-то не сработает, скажите, подберём другую.) Прицел рисует скрипт, свой нужно убрать.
4. Сделайте скриншот в формате **16:9**, лучше 1920×1080. Скрипт принимает `.png` и `.jpg`.

   Скриншот не 16:9? Скрипт подрежет его по центру до 16:9 и напишет об этом предупреждение. Прицел при этом остаётся в центре.
5. Сохраните скриншот в `content/<карта>/screens/` под **именем лайнапа** (см. ниже).

### Что получится из одного скриншота

Скрипт делает две картинки:

| Файл | Где используется | Что на нём |
|---|---|---|
| `gen_<карта>_<id>_stand.jpg` | тренировка (вопрос) | **целый** кадр без прицела (половину со случайным сдвигом на каждом вопросе вырезает приложение) |
| `gen_<карта>_<id>_howto.jpg` | поиск (нижняя панель) | центральная половина кадра **с прицелом** (нарисованным скриптом или вашим из игры, см. ниже) |

### Два способа получить кадр «как бросать»

| Что вы кладёте в `content/<карта>/screens/` | Что получится в Поиске |
|---|---|
| только `<id>.png` (без худа) | скрипт сам рисует маленький зелёный прицел в центре |
| `<id>.png` (без худа) **и** `<id>_howto.png` (с худом и вашим прицелом) | берётся центральная половина `<id>_howto.png` как есть, прицел не рисуется |
| `<id>.png` и `<id>_howto.gif` | в Поиске показывается GIF (если лежат и GIF, и `_howto.png`, побеждает GIF) |

Насколько крупно кадр показывается в Поиске, задаёт необязательный ключ `howto_zoom` (тот же принцип, что у `zoom`: `1` весь кадр, `1.5` две трети по центру, `2` половина по центру, это значение по умолчанию). Нужен, когда ориентир далеко от прицела и в центральную половину не попадает. На GIF ключ не влияет.

Для варианта с худом сделайте второй скриншот с той же позиции и тем же прицелом, но без `cl_drawhud 0`. Он тоже должен быть 16:9. Подрезается по центру так же, как основной. В тренировке всегда используется только `<id>.png`.

## 3. Нейминг (самое важное)

Имя файла скриншота = **id лайнапа** из `lineups.txt`. Только строчные латинские буквы, цифры и `_`.

Рекомендую единую схему: `cache_<граната>_<цель>_from_<позиция>`:

```
cache_smoke_a_site_from_garage.png
cache_flash_b_site_from_sun_room.jpg
```

- Две разные позиции на одну цель = два разных лайнапа и два скриншота (`..._from_garage`, `..._from_t_mid`).
- Одна позиция на разные цели = тоже два лайнапа и два скриншота.
- **GIF вместо картинки с прицелом** (необязательно): положите `<id>_howto.gif` рядом, например `cache_smoke_a_site_from_garage_howto.gif`. Тогда в панели «Как бросать» вместо готового кадра с прицелом покажется GIF. Держите GIF до 5 МБ.

Если имя скриншота не совпадёт с id в `lineups.txt`, скрипт сам об этом скажет.

## 4. Файл `content/<карта>/lineups.txt`

Каждый лайнап — блок, начинающийся с его id в квадратных скобках:

```
[cache_smoke_a_site_from_garage]
grenade     = smoke
side        = t
area        = a
title       = Смок на A
throw       = jump + lmb
origin      = garage | Garage | setpos 1400.5 1400.2 128.0;setang 12.3 45.6 0.0
target      = a_site | A site | setpos -170.0 1786.0 64.0;setang 0 0 0
description = Встаньте на ящик, прицельтесь в угол окна и бросьте с прыжком.
```

| Ключ | Что писать | Допустимые значения |
|---|---|---|
| `grenade` | тип гранаты | `smoke`, `flash`, `molotov`, `he` |
| `side` | за кого лайнап | `t`, `ct` |
| `area` | область цели | `a`, `b`, `mid` |
| `title` | подпись вопроса в тренировке | любой текст («Смок в окно») |
| `throw` | способ броска: части через `+` (см. ниже) | `ctrl`/`shift`, `forward_run` и др., `jump`, `lmb`/`rmb`/`lmb_rmb` |
| `origin` | откуда бросают | точка (см. ниже) |
| `target` | куда летит граната | точка (см. ниже) |
| `description` | текст в нижней панели | необязательно |
| `tolerance` | радиус зоны попадания в долях ширины показанного кадра | необязательно, по умолчанию `0.01` |
| `zoom` | во сколько раз увеличивается кадр в тренировке | необязательно, по умолчанию `2`, допустимо от `1` до `5` |
| `howto_zoom` | во сколько раз кадр «как бросать» в Поиске крупнее целого кадра (как `zoom`, только для Поиска) | необязательно, по умолчанию `2` (центральная половина), допустимо от `1` (кадр целиком) до `5` |

Строки, которые начинаются с `#`, игнорируются (можно писать заметки).

### Как записывать способ броска (`throw`)

Бросок складывается из четырёх независимых частей, которые пишутся через `+` в любом порядке. В приложении им соответствует экран выбора: слева клавиша, в центре восьмиугольник движения (тап по сектору: одна стрелка шаг, повторный тап две стрелки разбег, центр «стоять»), внизу «Прыжок» и мышь.

| Часть | Значения | Если не указать |
|---|---|---|
| клавиша | `shift` (идти шагом), `ctrl` (присесть) | клавиша не зажата |
| движение | `forward_step`, `forward_run`, `back_step`, `back_run`, `left_step`, `left_run`, `right_step`, `right_run` (`step` = шаг, `run` = долгий разбег) | стоя |
| прыжок | `jump` | без прыжка |
| кнопки мыши | `lmb`, `rmb`, `lmb_rmb` | **обязательно указать одну** |

Примеры:

```
throw = lmb                              # стоя, левая кнопка
throw = jump + lmb                       # jumpthrow на месте
throw = forward_run + jump + lmb         # с разбега вперёд, jumpthrow
throw = ctrl + forward_step + rmb        # присесть, шаг вперёд, правая кнопка
```

В тренировке ответ верен, только если совпали **все** четыре части.

### Как записывать точки

Точка — это позиция или цель. Записывается в формате `id | Название | координаты`.
- **Координаты** — прямо то, что выдаёт `getpos` в консоли, целиком: `setpos 1400.5 1400.2 128.0;setang 12.3 45.6 0.0`. Скрипт возьмёт из неё X и Y (высоту и углы игнорирует). Можно написать и просто два числа: `1400.5 1400.2`.
- **Первый раз**, когда точка встречается, пишите все три части.
- **Повторно** (позиция уже была в другом лайнапе) пишите только id: `origin = garage`. Так одна и та же точка не размножается и не расходится по координатам. Если случайно напишете те же id с другими числами, скрипт скажет об этом.
- `getpos` на месте падения гранаты даёт координаты **цели**, `getpos` там, где вы стоите — **позиции**.

### Как в тренировке показывается кадр

Скрипт сохраняет для тренировки **целый кадр**, а приложение на **каждом вопросе** само показывает его часть (по умолчанию половину, то есть увеличение вдвое; см. `zoom` ниже) со **случайным небольшим сдвигом**: точка прицела оказывается не в центре, а чуть в стороне (по горизонтали на 10–38 %, по вертикали на 5–38 % показанного кадра). Один и тот же лайнап при каждом появлении выглядит по-разному. Правильное место приложение считает само, ничего задавать не нужно.

По горизонтали сдвиг идёт в любую сторону, по вертикали всегда вниз от центра. Так окно уходит вверх и не захватывает гранату в руке из правого нижнего угла.

Почему так: зона попадания (по умолчанию радиус `0.01` ширины показанного кадра, около 3,5 dp) в самой игре покрывает вдвое меньший угол, чем на целом кадре. Если зону хочется шире или уже, меняйте `tolerance` у конкретного лайнапа. Кадр туториала (с прицелом) всегда по центру и не зависит от `zoom`.

### Зум кадра для каждого лайнапа: `zoom`

`zoom` задаёт, во сколько раз кадр увеличивается в тренировке:

```
zoom = 3
```

| zoom | что видно |
|---|---|
| `1` | кадр целиком (сдвига нет) |
| `1.5` | две трети кадра |
| `2` | половина кадра (по умолчанию) |
| `3` | треть кадра |
| `4` | четверть кадра |

Чем больше зум, тем **точнее** нужно целиться в игре, а размер зоны под палец на экране остаётся прежним (`tolerance` считается от показанного кадра). Дробные числа пишите через **точку** (`2.5`, не `2,5`).

Маленький зум (меньше 2) показывает больше кадра и может захватить гранату в руке из правого нижнего угла. Если она попадает в кадр, скрывайте её при скриншоте (`r_drawviewmodel 0`).

## 5. Запуск

Из корня проекта (в терминале Android Studio, вкладка Terminal):

```bash
python tools/convert_lineups.py
```

Только проверить пак, ничего не записывая:

```bash
python tools/convert_lineups.py --check
```

Что делает скрипт:
1. Находит все карты (`content/<карта>/lineups.txt`), проверяет `lineups.txt` каждой и наличие скриншотов. **Если что-то не так, пишет все ошибки сразу и ничего не меняет.**
2. Создаёт картинки `gen_*` в `app/src/main/res/drawable-nodpi/` (старые `gen_*` удаляет, остальные ваши файлы, например радар, не трогает).
3. Создаёт для каждой карты файл `app/src/main/java/.../data/<Карта>Generated.kt` (например `CacheGenerated.kt`) с её лайнапами.

Дальше в Android Studio: **Build → Make Project**, затем запускайте приложение. Если в `lineups.txt` нет ни одного лайнапа, приложение откроется, но списки будут пустыми.

Файлы `gen_*` и `CacheGenerated.kt` **вручную не редактируйте**: при следующем запуске скрипт их перезапишет.

## 6. Типичные ошибки

| Сообщение скрипта | Что делать |
|---|---|
| `не найден скриншот` | имя файла не совпало с id в `[...]` или он лежит не в `content/<карта>/screens/` |
| `файл ... не относится ни к одному лайнапу` | опечатка в имени скриншота (или лайнап не описан в txt) |
| `точка '...' ещё не описана` | точка использована в `origin`/`target` раньше, чем описана полностью: при первом использовании пишите `id | Название | координаты` |
| `уже описана с другими координатами` | в двух лайнапах одна и та же точка с разными числами: поправьте цифры или дайте разные id |
| `Допустимо: ...` | неверное значение (`grenade`, `side`, `area`, `throw`) |

Файл `lineups.txt` сохраняйте в кодировке **UTF-8** (Блокнот Windows по умолчанию так и делает). Русский в названиях и описаниях поддерживается.

## 7. Сколько делать для старта

Для проверки всего приложения хватит **6–10 лайнапов**: по 2–3 на тип гранаты, хотя бы одна цель с двумя позициями и хотя бы одна позиция с двумя целями. Остальное можно добавлять постепенно: запускайте скрипт заново после каждой партии.

Если нужной области нет (например, «Highway»), её надо добавить в `enum class Area` в `domain/Models.kt` и в таблицу `AREAS` в начале `tools/convert_lineups.py`. Напишите мне, сделаю.

## 8. Новая карта (например Mirage)

Чтобы добавить карту, нужно название и радар. Остальное делает скрипт.

1. Создайте папку `content/mirage/`: название карты строчными латинскими буквами и цифрами (`mirage`, `dust2`...).
2. Положите в неё радар: `radar.png` (или `radar.jpg`), **квадратная** картинка. Исходник радара в git не попадает, в репозиторий кладётся его сжатая копия.
3. Запустите `python tools/convert_lineups.py`. Скрипт сам создаёт всё, чего не хватает:
   - папку `screens/`;
   - `lineups.txt` с тестовым лайнапом `testlineup` (в приложении `mirage_testlineup`; смок под ноги в центре карты, сторона T, область «Мид», стоя + ЛКМ) и белый скриншот для него;
   - файл `app/src/main/java/.../data/MirageData.kt` с названием карты («Mirage») и **временной калибровкой** радара;
   - сжимает радар до 1536 px и кладёт его в `res/drawable-nodpi/mirage_radar.png`;
   - обновляет `data/GeneratedMaps.kt` (список всех карт приложения) и `data/MirageGenerated.kt` (лайнапы).

   Если радара ещё нет, заготовки всё равно создаются, а скрипт просит положить радар и запустить его снова.
4. Build → Make Project и запуск: когда карт больше одной, появляется переключатель карт.
5. **Калибровка радара.** В `MirageData.kt` значения `posX`, `posY`, `scale` временные (радар центрирован на нулевых игровых координатах), там же стоит `TODO`. Подберите настоящие: стартовые числа из `de_mirage.txt` (`pos_x`, `pos_y`, `scale`), но на Cache они давали сдвиг до 45 px, поэтому проверьте по нескольким точкам. Запишите `getpos` в 3-4 заметных местах и посмотрите, где они ложатся на радар; если мимо, пришлите точки и места на радаре, параметры подберутся методом наименьших квадратов.
6. Замените тестовый лайнап своими. Заготовки создаются только когда соответствующих файлов нет, поэтому удалённый тестовый лайнап скрипт не вернёт. Файл `MirageData.kt` после создания можно править руками (название, калибровка), скрипт его не перезаписывает.

Что важно знать:
- Первая карта в списке (по алфавиту названий папок) выбирается при запуске приложения.
- Id лайнапов уникальны только внутри карты (дубликат в одном `lineups.txt` скрипт не пропустит). Лайнапы можно спокойно копировать между картами вместе со скриншотами: итоговые id получат префикс своей карты.
- Чтобы заменить радар, положите новый `radar.png` в папку карты и запустите скрипт.
- Если нужной области нет в `enum Area` (`domain/Models.kt`), добавьте её туда и в таблицу `AREAS` в начале скрипта. Экран Тренировки показывает только области, которые есть на выбранной карте.
- Карты с двумя этажами (например Nuke и Vertigo) одним радаром не покрываются, для них нужна отдельная доработка.
- Проверка без записи и без создания файлов: `python tools/convert_lineups.py --check`.
